# FSOI for OCELOT — documentation index

Author: Azadeh Gholoubi. Last reviewed 23 September 2026.

Run every command from the `gnn_model/` directory.

## What this study is

Gradient-based forecast sensitivity to observation impact (FSOI) for OCELOT, an
observation-driven forecasting model, validated against the finite changes it is
meant to approximate. `FSOI_WORK_EXPLAINED_SIMPLY.md` describes the design, the
experiments and the results; this page is the index and the operating manual.

The manuscript and its supporting information are the authoritative statement of
results. They live in `FSOI/fsoi_outputs/paper_figures_v2/`. **No document in
this folder should be cited for a number that the manuscript also reports.**

## Canonical workflow

A frozen-metric evaluation is launched through one runner, configured entirely by
environment variables:

```bash
CONFIG_FILE=FSOI/configs/generated/<name>.yaml \
FSOI_OUTPUT_DIR=FSOI/fsoi_outputs/<new_dir> \
FSOI_START_DATE=2025-07-01 FSOI_END_DATE=2025-07-31 \
OSE_INSTRUMENTS=radiosonde OSE_DENIAL_MODE=background_replacement \
sbatch FSOI/scripts/run_fsoi_target_metric.sh
```

Notes that have bitten before:

- `sbatch --export` splits its own value list on commas, so any multi-value
  setting (instrument lists, path `t` values, pair indices) must travel
  **colon-separated**. The runner accepts commas, colons or semicolons.
- The runner refuses to write into an existing `FSOI_OUTPUT_DIR`.
- Configs are generated by `make_target_metric_config.py`; the generated ones
  live under `FSOI/configs/generated/`.

Purpose-built submissions wrap that runner:

| Script | Purpose |
|---|---|
| `scripts/submit_fsoi_sampling_final.sh` | The seasonal evaluations with inclusion-weighted source aggregation |
| `scripts/submit_endpoint_check.sh` | Rebuilds the background endpoint with missing-flagged entries held at control |
| `scripts/submit_directional_coverage.sh` | Directional gradient checks for the surface and aircraft metrics |
| `scripts/submit_path_convergence.sh` | Path integration at 9 and 17 points |
| `scripts/submit_combined_path.sh` | Per-instrument residuals along the combined path |
| `scripts/submit_combined_maps.sh` | Re-runs the seasonal evaluations saving 5° grids |

## Implementation invariants

These are properties of the pipeline, not options. Breaking any of them
invalidates the attribution.

1. **Sequential, deterministic cycle order.** The background for cycle *k* is the
   forecast launched from cycle *k−1*, so the dataloader runs with `shuffle=False`
   over chronologically sorted bins. Shuffling severs the chain between windows.
2. **Gradients are taken with respect to the input observations**, not the
   verification truth and not the model parameters. `xa` comes from the current
   window's inputs, `xb` from forecasting the previous window forward and decoding
   at the current input locations, and the increment is `d = xa − xb` in the same
   observation space.
3. **A failed gradient check skips the pair.** Gradients must be finite and
   non-trivial; a pair that fails is dropped rather than written out.
4. **The frozen metric is verified on reuse.** A checksum over target values,
   masks, coordinates and pressure indices is compared with the original at each
   reuse, and the calculation halts on a mismatch.
5. **First-of-month cycles are not scored.** Each monthly evaluation series opens
   at 12 UTC on day 1, whose background comes from the series' opening window
   rather than from a preceding cycle; that pair is excluded by valid time, not by
   rank. Any pooling that ignores this silently scores too many cycles and shifts
   every per-instrument mean.

## Plotting

All plotting lives in `FSOI/plotting/`. Run the scripts from `gnn_model/`.

The figures in the submitted manuscript are produced by dedicated scripts, each
drawn at final print size (165 mm wide, 8 pt Arial minimum, 600 ppi raster plus
vector PDF). Each is self-contained: it loads its own inputs and needs no other
plotting module, apart from the two channel figures noted below.

```
plotting/plot_fig1_framework_jgr.py          plotting/plot_figS1_innovation_jgr.py
plotting/plot_fig2_closure_innovation.py     plotting/plot_figS2_channel_impact_jgr.py
plotting/plot_fig3_path_integration_jgr.py   plotting/plot_figS3_error_distribution_jgr.py
plotting/plot_fig4_instrument_impact_jgr.py
plotting/plot_fig5_atms_cross_target_jgr.py
plotting/plot_fig6_maps_jgr.py
```

Two cautions carried by those scripts:

- `plot_fig5_atms_cross_target_jgr.py` and `plot_figS1_innovation_jgr.py` read
  their inputs through `FSOI_SEASONAL_ROOT`, which must point at a run family
  that carries per-variable, per-level stratification.
- `plot_fig5_atms_cross_target_jgr.py` and `plot_figS2_channel_impact_jgr.py`
  import the channel layout and the pooled scoring from their base figures
  (`plot_atms_cross_target.py` and `plot_fig4_instrument_impact_jgr.py`),
  so the pooling rule — first-of-month cycles excluded — is defined once.

The remaining scripts in `plotting/` are the per-run diagnostics invoked by the
submission scripts in `FSOI/scripts/`: gridded maps, innovation diagnostics,
channel heatmaps, pressure stratification and OSE comparison.
